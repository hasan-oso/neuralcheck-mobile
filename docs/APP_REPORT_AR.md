## ١. ما هو التطبيق؟ (ملخص تنفيذي)

**NeuralCheck** تطبيق يقيس الحالة الفعلية لهاتف مستعمل قبل بيعه/شرائه/إصلاحه، ويصدر **درجة A/B/C/D** مدعومة بتقرير تشخيصي. فكرته الجوهرية: لا يكتفي بقراءة المواصفات، بل **يُجهِد العتاد فعلياً** (معالج، رسوميات، بطارية، تخزين، حرارة) لمدة ٨–١١.٥ دقيقة بينما يسجّل سلسلة زمنية من القياسات، ثم يحلّلها.

ثلاثة أنماط فحص:
- **فحص عام** (`general`) — تقييم شامل للجهاز.
- **فحص ما قبل الإصلاح** (`pre_repair`) و**ما بعد الإصلاح** (`post_repair`) — مع مقارنة قبل/بعد (للفنّيين).

ثلاث أفكار مميِّزة تجعله مختلفاً عن تطبيقات «معلومات الجهاز» العادية:
1. **التمويه بالذكاء الاصطناعي:** يستخدم استدلال TensorFlow Lite (نماذج MobileNet) كحِمل إجهاد بدل النوى الاصطناعية، لأن أنظمة OEM المقيَّدة (HyperOS, ColorOS) لا تخنق أحمال «الذكاء الاصطناعي المشروع» — فيتمكن الفحص من الوصول للترددات الحقيقية للمعالج.
2. **«الكود يجمع، الذكاء الاصطناعي يحكم»:** في النسخة التجارية يُرسَل القياس الخام كاملاً إلى خادم Firebase ليصدر الحكم نموذج لغوي كبير، بدون تلخيص محلي.
3. **بصمة جهاز مجهولة من ٥ طبقات** (SHA-256) — الطبقتان المعرِّفتان B (Firebase Installation ID) وC (ANDROID_ID) تُهشَّران منذ P0.1.

## ٢. المعمارية والتقنيات

البنية **MVVM + Clean Architecture** بثلاث طبقات:

```
Presentation (Compose + ViewModels)
        ↓
Domain (Use Cases + ScoringEngine + Models)
        ↓
Data (Room DB + ملفات GZIP JSON + Repositories)  ←→  Service/Hardware (الإجهاد + الاستشعار)
```

| البند | القيمة |
|---|---|
| اللغة / الـ UI | Kotlin · Jetpack Compose · Material Design 3 |
| حقن التبعيات | Hilt (حقن عبر المُنشئ في كل مكان) |
| التزامن | Coroutines + Flow (لا RxJava) |
| قاعدة البيانات | Room (SQLite) + ملفات `.ts.json.gz` للسلاسل الزمنية |
| الخلفية | WorkManager (مزامنة) + Foreground Service (الإجهاد) |
| العتاد | Camera2 · OpenGL ES 3.1 (Compute) · NDK/C++ (NEON) · Sensors |
| السحابة | Firebase BOM 32.7.0 (Firestore · Storage · Functions · Auth · Messaging) |
| الذكاء الاصطناعي على الجهاز | TensorFlow Lite 2.16.1 (+GPU delegate) |
| متفرقات | ZXing (QR) · Vico (رسوم بيانية حية) · Gson · Google One-Tap |
| الحدّ الأدنى/الهدف | minSdk **28** (أندرويد 9) · target/compile SDK **35** |
| المعمارية الأصلية | **arm64-v8a فقط** · NDK 27.1 (كل الأجهزة المدعومة 64-بت، NEON إلزامي) |

المكوّنات المُعلَنة في الـ Manifest: نشاط واحد (`MainActivity`)، خدمتان (`StressTestService` من نوع `dataSync`، و`NeuralCheckMessagingService` للإشعارات)، و`FileProvider` للمشاركة. الصلاحيات تشمل: الكاميرا، الموقع الدقيق، حالة الهاتف، الميكروفون، البلوتوث/NFC، الإشعارات، والخدمة الأمامية.

## ٤. رحلة المستخدم والواجهة

الطبقة كلها Compose + Material 3، نشاط واحد (`MainActivity` وهو `FragmentActivity` لأن مطالبة البصمة البيومترية تحتاج مضيف Fragment). الخريطة في `presentation/navigation/NeuralCheckNavigation.kt`.

### بوابة البداية المشروطة
- **النسخة التجارية:** تبدأ من `home` إن كان المستخدم مسجَّلاً، وإلا `login`.
- **النسخة الداخلية:** تبدأ دائماً من `home` (بلا مصادقة أبداً).

### المسارات الرئيسية (٢٣ مساراً)
`login` · `onboarding` · `home` · `qr_scanner` · `pre_scan/{type}/{linked}` · `active_scan/...` · `manual_tests/{id}` · `report/{id}` · `tech_pre_repair` · `tech_post_repair` · `comparison/{a}/{b}` · `peer_survey/{id}` · `history` · `settings` · `profile` · `subscription` · `payment/{plan}` · `shop_setup` · `scan_history` · `payment_history` · `generate_session` · `join_session`.

### تدفّق الفحص (القلب التفاعلي)
1. **PreScan** — قائمة شروط حيّة تُحدَّث كل ثانيتين (بطارية، شاحن، حرارة، مدة التشغيل، إغلاق التطبيقات، سطح مستوٍ) بألوان أخضر/أصفر/أحمر. زر البدء معطَّل عند وجود أي حاجب أحمر. هنا تُفحص بوابة الاشتراك أيضاً.
2. **ActiveScan** — تُبقي الشاشة مضاءة، وتعرض: اسم المرحلة + مؤشّر النقاط، شريط تقدّم متدرّج، نصائح أمان دوّارة، و**رسمَين بيانيَّين حيَّين عبر Vico** (استخدام المعالج، وحرارة البطارية مع خط خطر ٤٥°)، وشبكة ٢×٢ من البطاقات (حرارة، استخدام، وقت متبقٍّ، نسبة البطارية). الرسوم تُجبَر على اتجاه LTR حتى في واجهة عربية RTL.
3. **ManualTests** — جامع الاختبارات اليدوية بعد الفحص (بكسلات ميتة، لمس، مكبّرات صوت، ميكروفونات، أزرار، منفذ شحن، كاميرات، بصمة/وجه...). أي اختبار لا يُجاب عليه يُسجَّل `not_tested` لضمان مصفوفة نتائج كاملة للذكاء الاصطناعي.
4. **Report** — التقرير النهائي (يتفرّع حسب النكهة، انظر أدناه)، مع شريط سفلي: مشاركة / QR / حفظ PDF.

### تفرّع التقرير حسب النكهة (أكبر فرق في الواجهة)
- **التجارية (AI):** يعرض فقط قسم الذكاء الاصطناعي — شارة الدرجة + الملخّص + الحكم + المشكلات (ملوَّنة بالخطورة) + السبب الجذري + نصائح المشتري (عادي/لاعب/مصوّر) + المشكلات المتوقَّعة. عند فشل الخادم: بطاقة خطأ مع زر إعادة المحاولة، **بلا أي تسريب للتقييم بالقواعد**.
- **الداخلية (قواعد):** شبكة المحاور ٢×٢ + صفوف الفئات + بطاقة الأعطال الحرجة + لافتة مكافحة التلاعب + الاختبارات اليدوية ضمن التقرير.

### المظهر واللغة
- **تصميم داكن دائماً** (يتجاهل وضع النظام عمداً) لإبراز ألوان الدرجات وتوفير البطارية أثناء الفحص الطويل. خلفية `DeepSpace #0A0E1A`، لون العلامة `NeuralGreen #4ADE80`.
- **ألوان الدرجات:** A أخضر `#22C55E` · B أزرق · C برتقالي · D أحمر.
- **خطّان من Google Fonts وقت التشغيل:** `Tajawal` للنصوص العربية، و`Outfit` للأرقام والوحدات التقنية.
- **التوطين:** العربية افتراضية (RTL) + التركية. ملف العربية ~٩٨٦ سلسلة، التركية ~٨٣٠. نظامان متوازيان: توطين أندرويد القياسي للواجهة، ومفاتيح مزدوجة `_ar`/`_tr` (~٢٣٧ مفتاحاً) لأسماء النماذج التي تحملها طبقة التقييم كحقول. تبديل اللغة عبر `util/LocaleHelper.kt` ثم `Activity.recreate()`. الأرقام تُحوَّل إلى اللاتينية دائماً عبر `NumberFormat.toLatin`.

> 🔎 **ملاحظتان:** مسار `comparison/{a}/{b}` وشاشة `OnboardingScreen` مُنفَّذان بالكامل لكنهما **غير مُستدعَيَين** حالياً في الكود الحي (يتيمان).

## ٥. محرك فحص الضغط (القلب النابض)

`StressTestService` (في `service/stress/StressTestService.kt`، ~١٨٠٠ سطر) هو `LifecycleService` وحيد يستضيف **مسارَين** للإجهاد جنباً إلى جنب، يُختاران وقت البناء.

### دورة الحياة والأمان قبل الإقلاع
- يبدأ كخدمة أمامية (`FOREGROUND_SERVICE_TYPE_DATA_SYNC`) خلال ~٥ث مع إشعار تقدّم، ويحجز `PARTIAL_WAKE_LOCK` بمهلة تتجاوز مدة الفحص.
- **بوابة ما قبل الإقلاع** ترفض البدء بأسباب صريحة: بطارية < **٤٠٪** · حرارة بطارية > **٣٨°** · شاحن متصل (يلوّث قياس الاستهلاك) · مساحة كاش < **٦GB** · ذاكرة حرة < **١GB** · وضع توفير الطاقة.
- التهيئة، حفظ سجل الفحص في Room فوراً، توليد بصمة الجهاز، وكتابة ترويسة السلسلة الزمنية. آلة الحالة `ScanState`: `Idle → Running → Completed/SafetyStopped`. الإنهاء (`completeScan`) محميّ بـ `AtomicBoolean` ويُغلَّف بـ `NonCancellable` كي لا يُفقد التذييل/البيانات إذا أغلق النظام الخدمة.

### V1 مقابل V2 (الفرق الجوهري)
| | **V1 (datacollect)** | **V2 (launch)** |
|---|---|---|
| المدة/المراحل | ٦٩٠ث / ٥ مراحل | ٤٨٠ث / ٨ مراحل |
| المعالج | JVM، ضرب مصفوفات 128×128 | NDK NEON، **كل النوى الثمانية** بتثبيت تقارب لكل عنقود |
| الرسوميات | OpenGL ES 2.0 | ES 3.1 (Compute) + raymarching |
| الحِمل | نوى اصطناعية | **استدلال TFLite حقيقي** (تمويه) |

**مراحل V2 الثمانية:** `INIT_PROFILING(30ث)` → `STORAGE_STRESS(75ث، كتابة مستمرة بسعة حتى 4GB)` → `MEMORY_STRESS(60ث)` → `CPU_SUSTAINED(75ث، 4Hz)` → `GPU_SUSTAINED(75ث، 4Hz)` → `COMBINED_PEAK(60ث)` → `BURST_PATTERN(45ث، 10Hz، فحص هبوط الجهد)` → `COOLDOWN(60ث)`. القائد (`phaseDriver`) مدفوع بالأحداث: يستقصي المرحلة الفعلية كل ٥٠٠م.ث ويقدّم العيّان وفقها.

### حِمل المعالج (V2)
نواة C++ أصلية (`libstress.so`) تكتشف طوبولوجيا العناقيد (big/mid/little) عبر ترددات `cpuinfo_max_freq`، فتُشغّل العمّال الثقال (NEON FMA matmul) على النوى الكبيرة والمتوسطة، وعمّالاً خفافاً على النوى الصغيرة — **مع حجز نواة صغيرة واحدة لخيط العيّان**. التحقّق ذاتي المرجع (مقارنة بصمة النتيجة بت-ببت). فشل تثبيت التقارب (تحت Knox/MIUI) غير قاتل ويُسجَّل كقياس عن بُعد.

**كشف خنق النظام (Governor capping):** مراقب يبدأ بعد ١٠ث من المرحلة ٣؛ إن أظهرت ٥ قراءات متتالية أن تردد النواة الكبيرة < ٧٠٪ بينما يُبلّغ النظام أنه «بارد» (خنق بالسياسة لا بالحرارة) → يُسجَّل ويُتخطّى ٤/٥/٦ (فحص ~٣ دقائق بدل ٨).

### التمويه بالذكاء الاصطناعي (TFLite)
الهدف الصريح: جعل الإجهاد **غير قابل للتمييز عن مقياس أداء ذكاء اصطناعي مشروع** كي لا يخنقه النظام. يُحمَّل `mobilenet_v3_large/small` (حسب فئة الجهاز)، ويُختار المُسرِّع NNAPI → GPU → CPU. كل عامل متوازٍ يملك مُفسِّره الخاص (TFLite غير آمن للخيوط)؛ وعند غياب المكتبة يسقط لوضع STUB حتى يبقى المسار يعمل. الإشارة القانونية على «أن الفحص جرى فعلاً» هي `aiInferenceIterationsTotal` + المُسرِّع النشط في التذييل.

### العيّان والأمان والمعايرة
- **DisciplinedSampler:** خيط مجدوِل وحيد يلتقط لقطات ذرّية بتردد 1Hz/4Hz/10Hz. مخطّطان: V1 بـ ١٨ قناة، V5 بـ **١١ قناة**. القنوات المحجوبة (حرارة المعالج/الرسوميات، التسارع) نُقلت إلى التذييل مع أعلام توفّر صريحة بدل قيم `-1` الغامضة.
- **SafetyMonitor:** يفحص كل **٢٥٠م.ث** بأربع قواعد قاتلة للفحص كله: حرارة بطارية > ٤٥° · حرارة معالج > **٩٧°** (الثابت الفعلي، رغم أن التعليق يقول ٩٠) · استهلاك > ١٥٪ خلال ٣ دقائق · بطارية < ١٠٪.
- **المعايرة النسبية** (`USE_RELATIVE_CALIBRATION`، **مُطفأة في كل بناء مُلتزَم**): مرحلة فحص أوّلي تقيس قدرة كل نظام فرعي وتضبط معاملات الحِمل وفقها.

### معيار الإشباع (هل أجهد الفحصُ الرقاقةَ فعلاً؟)
استُبدل المعيار الأحادي القديم (تردد ≥ ٠.٨٥) بمعيار **رباعي المحاور C1–C4** (لأن إدارة الطاقة الحديثة تُبقي التردد عند ٦٠–٧٠٪ تصميمياً): C1 ذروة استطلاك ≥ ٤٠٠٠م.واط · C2 انشغال حوسبي مستمر (٣ مسارات) · C3 سلامة التحقّق · C4 قدرة ذروة التردد ≥ ٠.٨٥. تحقُّق ٤/٤ = «مُشبَع كلياً»، ٣/٤ = «مُشبَع فعلياً» مع تحفّظ، ≤٢ = فشل. هذه الإشارة تُخبر الذكاء الاصطناعي بأن القيم الحميدة تعني جهازاً سليماً لا نظاماً خنق الحِمل.

## ٦. الاختبارات الوظيفية الـ ١٢٠

ينسّقها `FunctionalTestRunner` (`hardware/runner/FunctionalTestRunner.kt`) داخل `supervisorScope` (فشل فئة لا يُسقط البقية). كل اختبار يُمثَّل بـ `TestResult{testId, الاسم, الفئة, status, score?, rawValue?, الوحدة, notes}`، والحالات: `PASS/FAIL/WARNING/UNAVAILABLE/NOT_TESTED/ERROR`.

> تمييز مهم: `UNAVAILABLE` = العتاد غير موجود · `NOT_TESTED` = الصلاحية مرفوضة (لا يُعاقَب الجهاز عليها) · `ERROR` = استثناء أثناء القياس.

| الفئة | المعرّفات | عيّنة مما يُقاس |
|---|---|---|
| 🔋 البطارية | B-01..B-08 | الصحة، السعة التصميمية، الحرارة، الجهد، التيار، التقنية، **عدّاد الدورات**، ومعدّل الاستهلاك تحت الحِمل (B-06 محسوب بعد الإجهاد) |
| 🧠 المعالج | C-01..C-07 | عدد النوى، أقصى تردد، تردد الراحة، **بنشمارك MFLOPS** (يُشغَّل منفرداً)، طراز الـ SoC، نسبة الخنق الحراري، استقرار الأداء |
| 🎮 الرسوميات | G-01..G-05 | معلومات GPU، دعم Vulkan، هبوط FPS، الخنق الحراري، أدنى FPS مستمر |
| 💾 التخزين | S-01..S-06 | السعة الكلية/المتاحة، قراءة/كتابة تسلسلية (MB/s)، قراءة/كتابة عشوائية (IOPS) عبر I/O حقيقي في الكاش |
| 🌡️ الحرارة | T-01..T-04 | أقصى حرارة، معدّل الارتفاع، معدّل التبريد (T-03 صار إعلامياً)، عدد المناطق الحرارية النشطة |
| 🧮 الذاكرة | R-01..R-03 | إجمالي RAM، المتاح (التقييم بالنسبة)، علم انخفاض الذاكرة |
| 📶 الخلوي | N-01..N-07 | إصدار الـ baseband (مودم ميت→FAIL)، حالتا شريحتَي SIM، نوع الشبكة، قوة الإشارة، المشغّل، دعم eSIM |
| 📡 اللاسلكي | N-08..N-13 | Wi-Fi (الحالة/السرعة/RSSI)، البلوتوث، BLE، NFC |
| 📍 GPS | L-01..L-03 | توفّر GPS، عدد الأقمار (انتظار ٣٠ث)، دقّة التموضع |
| 🎯 المستشعرات | SN-01..SN-12 | ١٢ مستشعراً (تسارع، جيرو، قُرب، ضوء، مغناطيس، ضغط، حرارة، خطوات، جاذبية، دوران...) بجمع ٣ث لكل واحد |
| 📷 الكاميرا/البيومتري | CM-01..CM-11 | كاميرات خلفية/أمامية/إضافية، فلاش، تركيز، دقّة (MP)، بصمة، وجه، هزّاز |
| 🖥️ الشاشة | D-01..D-03 | الدقّة، الكثافة (DPI)، معدّل التحديث (Hz) |
| 🔐 الأمان | SEC-01..SEC-11 | قفل الشاشة، التشفير، رقعة الأمان، **كشف الروت**، وضع المطوّر، USB، مصادر غير معروفة، إصدار النظام... |
| 🛠️ مُوسَّع (داخلي فقط) | INFO-01/02، SEC-12، SN-13 | كود المنطقة CSC، **IMEI مُقنَّع**، قفل الـ Bootloader، معايرة التسارع — **PII لا تُرفع أبداً في النسخة التجارية** |

**الاختبارات اليدوية M-01..M-22:** ليست كوداً تنفيذياً بل إجابات المستخدم في الواجهة، أُعيد توزيعها على فئات (شاشة/صوت/إدخال/بطارية/تخزين/مستشعرات/كاميرا/أمان) في تحديث ٢٠٢٦-٠٥-١٧ لمنع تضخيم درجة فئة بنتيجة من فئة أخرى.

## ٧. نظام التقييم رباعي الطبقات

مُعرَّف في `app/src/main/assets/scoring_config.json` (قابل للتعديل دون لمس الكود)، ويُطبَّق في `domain/scoring/RuleBasedScoringEngine.kt`.

```
الطبقة ١: درجة كل اختبار (0-100) — استيفاء خطّي حسب منحنيات العتبات
        ↓ (المتوسط الموزون، تُستبعَد UNAVAILABLE/NOT_TESTED)
الطبقة ٢: درجة الفئة (١٣ فئة، أوزان لكل اختبار)
        ↓
الطبقة ٣: درجة المحور (٤ محاور)
        ↓
الطبقة ٤: الدرجة الإجمالية → حرف A/B/C/D
```

**أوزان المحاور الإجمالية:** البطارية **٣٥٪** · الأداء **٣٠٪** · الاتصال **٢٠٪** · الأمان **١٥٪**.

**عتبات الحروف:** A: ٨٥–١٠٠ · B: ٧٠–٨٤ · C: ٥٠–٦٩ · D: ٠–٤٩.

### الأعطال الحرجة (CriticalPenaltyCalculator)
مودم ميت (N-01)، كاميرا لا تعمل (CM-01/02)، بلوتوث غائب (N-11)، روت (SEC-04)، استهلاك بطارية > ٢٪/د (B-06)، خنق حراري > ٧٠٪ (C-06)، بلوغ عتبة الأمان الحرارية (T-01)، ذاكرة منخفضة (R-03). كل عطل = خصم **١٠ نقاط** (بحدّ أقصى ٤٠)، **و** سقف للدرجة عند **٦٥** (أي C كحدّ أقصى). الفحص غير المكتمل يُسقَف عند **٥٥**.

### كشف التلاعب (AntiTamperDetector)
أربع علامات: بداية باردة مريبة (< ١٥°)، إعادة تشغيل حديثة (< ساعة)، نزع الشاحن لتوّه (حار + جهد عالٍ + شحن ~كامل)، حِمل خلفية ثقيل. التأثير الوحيد على الدرجة: **خصم ٥ نقاط فقط** عند بداية شديدة البرودة (< ١٠°)؛ بقية العلامات تظهر كتحذيرات في التقرير وتُرسَل للذكاء الاصطناعي.

### القواعد مقابل الذكاء الاصطناعي
- **القواعد** (`rule_based_v1`، النسخة الداخلية): حساب محلّي حتمي يملأ المحاور/الفئات/الأعطال.
- **الذكاء الاصطناعي** (`ai_v1`، النسخة التجارية، عبر `domain/scoring/AiScoringEngine.kt`): **الخادم هو المصدر الوحيد للحقيقة**؛ لا يُشغَّل التقييم بالقواعد إطلاقاً، ولا يوجد احتياطي محلّي عند الفشل. يُرسِل القياس الخام كاملاً، ويعيد حساب أعداد النجاح/الإجمالي محلياً ليطابق التقرير الاختبارات الفعلية.

**حالات الاستخدام:** `ExecuteStressTestUseCase` (تنسيق بيانات الفحص) · `GenerateReportUseCase` (التجميع + التقييم + الحفظ) · `CompareTwoScansUseCase` (فرق قبل/بعد: محسَّن/متدهور/ثابت) · `ExportDataUseCase` (تصدير ZIP كامل).

<a name="8"></a>
## ٨. طبقة البيانات والتخزين

«أوفلاين-أوّلاً»: Room للصفوف المهيكلة، ملفات GZIP-JSON للسلاسل الزمنية، و`EncryptedSharedPreferences` للإعدادات.

### قاعدة البيانات (Room، الإصدار ٤)
بنية نجمية: `ScanEntity` (الجذر) + أربعة أبناء بـ `CASCADE`: `FunctionalResultEntity` (صف لكل اختبار)، `TechnicianInputEntity`، `PeerInputEntity`، `ScanScoreEntity` (يخزّن أيضاً `aiAnalysisJson` كاملاً ليُعاد بناء التقرير دون استدعاء جديد). الهجرات كلها إضافية: 1→2 أضاف `shortId`، 2→3 أضاف `userId` (تصفية حسب الحساب)، 3→4 أضاف `aiAnalysisJson`.

### تنسيق السلسلة الزمنية `.ts.json.gz`
الجذر `{header, variables[], samples[], footer}`. أثناء الفحص يُكتب ملف مؤقّت سطراً-بسطر بعلامة `ACTIVE_SESSION:` (لاستعادة الأعطال)، ثم يُضغَط GZIP عند الإنهاء. **التذييل (Footer) هو المُدخَل الأساسي للذكاء الاصطناعي** ويحوي: أقصى الحرارات، التحقّقات، فعالية الإشباع (C1–C4)، **٦ مؤشّرات بطارية سلوكية**، جودة البيانات، `fieldsVersion`، وتشخيصات لكل حقل.

> **تصلّب ضد التلف:** الإنهاء يلتقط `Throwable` (لا `Exception` فقط) لمعالجة بق اقتطاع التذييل على Xiaomi MT6991، ويكتب نسخة احتياطية للتذييل قبل الضغط، ويُفعّل `serializeNulls()` للتمييز بين «حساب أنتج null» و«اقتطاع».

**معنى `fieldsVersion=63`:** ختم تطوّري لمخطّط التذييل. أبرز محطّاته: 60 = معيار الإشباع الرباعي · 61 = كسر مخطّط V5 (٢٢→١١ قناة) · 62 = كتلة المعايرة · **63 = كسر مخطّط البطارية**: حُذف تقدير «صحة البطارية» الأحادي (كان يعطي قيماً مستحيلة كـ ١٠٢٪ على S24 Ultra) واستُبدل بـ ٦ مؤشّرات سلوكية مقيسة أثناء الفحص الفعلي. الوثيقة العامة: `docs/architecture/BATTERY_INDICATORS.md`.

> ثلاثية إصدارات يجب عدم خلطها: **Room v4** (الصفوف) ≠ **fieldsVersion 63** (التذييل) ≠ **جيل قنوات `v[]`** (18/22/11، يُكتشف وقت القراءة من `variables.size`).

### بصمة الجهاز (٥ طبقات)
`util/DeviceFingerprint.kt`: مفتاح SHA-256 من خمس طبقات تتدهور بأمان: (A) توقيع RSA-2048 في TEE/KeyStore يصمد للضبط المصنعي · (B) Firebase Installation ID · (C) ANDROID_ID · (D) مركّب من Build · (E) كتالوج المستشعرات. الطبقتان B وC معرِّفتان للجهاز و**تُهشَّران (SHA-256) منذ P0.1**؛ قبل ذلك كانتا تُرسَلان خامَّتين.

<a name="9"></a>
## ٩. التكامل السحابي (Firebase)

مشروع `neuralchek-9b6d7`. **كل التكامل السحابي حصري للنسخة التجارية.**

### المصادقة
`data/auth/AuthManager.kt` يغلّف Firebase Auth بأربع طرق: **Google One-Tap** (الأساسية)، بريد/كلمة مرور، **مجهول** (لأجهزة الزبائن)، وإعادة تعيين كلمة المرور. سبب وجوب المصادقة: دوال Firebase القابلة للاستدعاء تتطلّب هوية.

> **تسجيل الخروج = مسح محلّي كامل:** يمسح صفوف Room، يُنهي ويُمسح كاش Firestore، يحذف مجلدات السلاسل الزمنية، ويُفرِغ حامل الجلسة — منعاً لتسرّب بيانات حساب إلى آخر على جهاز مشترك.

### المدفوعات والاشتراكات
ثلاث خطط: `single` (شحن إضافي) · `shop_basic` · `shop_pro`. لا يوجد Google Play Billing — بل **تحويل ShamCash يدوي**: يقرأ المستخدم رقم التحويل من Firestore، يحوّل خارجياً، ويلصق المرجع → `requestPayment` يسجّل طلباً معلّقاً يراجعه المكتب الخلفي. عند الموافقة يصل **إشعار FCM** يُطلق `SubscriptionRefreshBus` فتتحدّث الواجهة فوراً. البوابة الفعلية في `PreScanViewModel.checkAccess`: جلسة نشطة → سماح · نسخة داخلية → سماح · غير مسجَّل → تسجيل دخول · `scansRemaining <= 0` → لا أرصدة.

### جلسات متعدّدة الأجهزة (المتجر ↔ الزبون)
المشكلة: جهاز الزبون (تحت الفحص) بلا حساب، لكن `analyzeDevice` يتطلّب هوية. الحل: **sessionId** يربط الفحص بحساب صاحب المتجر:
1. المالك يُنشئ جلسة (`createScanSession`) → كود قصير + QR (`neuralcheck://session/{code}`) صالح ١٥ دقيقة، ويستمع لـ `scanSessions/{id}`.
2. الزبون يمسح/يكتب الكود → `joinScanSession` (يتخطّى المصادقة عمداً) → يُخزَّن sessionId في `ScanSessionHolder`.
3. عند التحليل: تسجيل دخول مجهول لإرضاء حارس الـ SDK، وإرسال sessionId، والخادم يفوتر على المالك. ثم يُمسح الحامل لمرّة واحدة.

### المزامنة والإشعارات والخادم
- **المزامنة:** `SyncWorker` (WorkManager) — دورية كل ٦ ساعات على Wi-Fi + `syncNow` فوري. يرفع ملف `.ts.json.gz` إلى Storage ووثيقة كاملة إلى `scans/{scanId}`.
- **مجموعتان متمايزتان:** `scans/{id}` يكتبها العميل، و`reports/{id}` تكتبها دالة `analyzeDevice` (الحكم القانوني الذي تقرؤه الواجهة).
- **AI Backend:** `data/remote/FirebaseAnalysisService.kt` يستدعي `analyzeDevice` (مهلة **٣٠٠ث**) ويُرسِل: `scanId` + بصمة سلوكية (معلومات الجهاز + النتائج الوظيفية + اليدوية + **السلسلة الزمنية الخام كاملةً** ~٢٧٠KB + أعلام التلاعب). يعيد: الدرجة/الحرف/الملخّص/الحكم/المشكلات/المشكلات المتوقَّعة/نصائح المشتري/`shortId`. **كل حقول الاستجابة nullable** (لأن Gson يتجاوز قيم Kotlin الافتراضية). **أولوية الكاش:** يُفحص `reports/{id}` أولاً لتجنّب فاتورة Gemini مزدوجة.
- **قواعد Firestore:** ملكية صارمة — `users/{uid}` للمالك، و`reports`/`payments`/`scanSessions` للقراءة فقط ومُقيَّدة بالمالك.

### حقن التبعيات (Hilt)
خمس وحدات: `AppModule` · `FirebaseModule` (Storage/Firestore) · `DatabaseModule` (Room + الهجرات + الـ DAOs) · `RepositoryModule` (ربط Impl→interface) · `EngineModule` (يختار `ScoringEngine` حسب العَلَم، ويحقن `AiScoringEngine` كـ `Lazy` كي لا يُبنى رسمه إلا في النسخة التجارية).

<a name="10"></a>
## ١٠. الأمان والخصوصية

- **خصوصية أوّلاً:** بصمة جهاز لا تحمل هوية شخصية؛ طبقتاها المعرِّفتان (Firebase Installation ID وANDROID_ID) **مُهشَّرتان منذ P0.1**. اختبارات الـ PII (IMEI مُقنَّع، CSC، Bootloader) **محصورة في النسخة الداخلية** ولا تُرفع للسحابة أبداً.
- **التشفير عند الراحة:** الإعدادات عبر `EncryptedSharedPreferences` (AES256) مع سقوط آمن لملف عادي إن فشل التشفير.
- **حدود أمان حرارية صارمة:** فحص كل ٢٥٠م.ث (بطارية ٤٥° / معالج ٩٧°) لمنع تلف العتاد.
- **عزل البيانات:** تسجيل الخروج يمسح كل أثر محلّي للحساب السابق.
- **مفاتيح التوقيع:** نُقلت إلى `keystore.properties` (خارج Git)، والـ debug يشارك مفتاح الإصدار لتسهيل التحديث دون فقدان بيانات.

## ١١. ملاحظات ونقاط تستحق الانتباه

رصدها الفحص المعمّق للكود (قد تستحق متابعة):

1. **انحراف توثيقي في `SafetyMonitor`:** التعليق والوصف يقولان «حدّ المعالج ٩٠°» بينما الثابت الفعلي **٩٧°** (`service/safety/SafetyMonitor.kt`).
2. **مسار `comparison/{a}/{b}` وشاشة `Onboarding` يتيمان** — مُنفَّذان لكن غير مُستدعَيَين في الكود الحي.
3. **مساران لكشف التلاعب:** `AntiTamperDetector` (٤ علامات، يحكم الخصم) و`GenerateReportUseCase.detectAntiTamperFlags` (علامتان فقط، يملأ التقرير) — لا يؤثّر على الدرجة لكنه ازدواج يستحق التوحيد.
4. **ثغرة محتملة في قواعد Firestore:** لا قواعد لـ `scans/` (يكتبها العميل) ولا لـ `settings/app` (يقرؤه `PaymentViewModel`) — قد تُرفَض تحت سياسة المنع الافتراضي ما لم تُضبَط في الكونسول (الكود يعوّض جزئياً).
5. **عدم تطابق أسماء بين `TestSpec` والتنفيذ الفعلي** لبعض المعرّفات (مثل C-03/C-05، G-05، N-13) — التنفيذ هو المرجع لما يُحسَب فعلاً، لا أسماء `TestSpec`.
6. **إزاحة بمقدار واحد** بين معرّفات CM-10/CM-11 وموارد النصوص المرتبطة بها.

## الخلاصة

NeuralCheck ليس «تطبيق معلومات جهاز»، بل **منصّة تشخيص هندسية** تجمع بين إجهاد عتاد حقيقي على مستوى النواة الأصلية (C++/NEON/OpenGL Compute)، وتمويه ذكي عبر TFLite لتجاوز خنق أنظمة OEM، وخطّ تحليل سحابي بنموذج لغوي كبير، وتصميم «أوفلاين-أوّلاً» يحترم الخصوصية. النضج واضح في تفاصيل المرونة (كل قراءة عتاد مُغلَّفة `runCatching`، ومبدأ «تدهور لا تنهَر»)، وفي التوثيق الغني داخل `docs/audits/` الذي يؤرّخ تطوّر المشروع عبر ١٤+ مرحلة تدقيق.
